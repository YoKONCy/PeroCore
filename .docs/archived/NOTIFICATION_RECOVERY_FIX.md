# 启动通知重复弹出的修复

截图中的图像编辑、图像生成结果来自持久通知的历史补送。原流程握手后发送全部 unread 通知，主界面展示后没有回执；前端去重集合只存在于内存，刷新或重启后再次弹出全部结果。主界面还丢弃了原始标题，只显示通用“错误／成功”。

## 修改

- 握手与角色切换补送携带原始时间、角色、修订号及 `replayed` 标记；Durable Stream 的游标恢复也标记为历史。
- 前端将历史结果合并为一个中性汇总提醒，保留失败数量。新失败照常即时显示原始标题和内容。
- 通知真正进入展示队列前台后才保存本地回执、向服务端批量确认。回执异常静默重试，不制造额外错误提示。本地记录按后端地址隔离，跨刷新生效。
- 通知回执仅更新通知记录，不修改任务本身、任务中心的未读状态、画布、文件或作品。
- 相同通知 ID 在后台重复投递不会再次推送；任务结果恢复保留原始完成时间，不伪装成新执行结果。
- 游标补送根据数据库未读状态过滤已确认的通知，保留最新序号，避免内存缓存再次回放旧结果。
- 同时展示最多三条 Toast，其余排队，排队期间不倒计时。卡片不再被 flex 压扁。
- 历史任务事件只恢复面板状态，不重新打开结果或发送 Windows 失败通知。

源码检查中，画布 `restoreRuns` 只恢复未结束任务并查询状态，已完成／失败任务不会因打开页面重新提交生成；宿主对已交接请求也使用持久幂等键恢复。

## 画布移除与通知联动

- Pictoria 提供 `task.dismissed` 查询，以及宿主兼容层使用的离线只读索引，按角色返回画布主动移除的任务标识。绘图后台关闭时不为了通知过滤而启动它。
- Gateway 在实时推送、启动补送与游标补送时统一过滤这些通知，并确认通知回执。过滤器读取或回执保存失败会记录日志，执行历史、任务状态、作品资源均不删除。
- 删除整个画布时，在同一事务中记录所属任务的通知移除标记。撤销节点移除会恢复索引可见性，但已经确认的旧通知不会重新变成未读。
- 历史通知汇总只接收过滤后仍需展示的通知，不以画布当前内容数量推断任务执行状态。
