### 📅 Project Vision

In the current AI explosion era, we've seen too many powerful tools — they are often **cold**, used and forgotten. What we want to build is an AI with real memory and warmth.

**PeroperoChat!** was born from our fundamental desire for a true "companion". We believe a real AI companion should have:

- **Real Memory**: Not just remembering what you said, but remembering the stories you shared, your preferences, and even habits you haven't noticed. It "associates" — when you mention "rainy day", it recalls the song you listened to together last time.
- **Proactive Care**: No longer just "ask and answer". It can understand your state and offer a caring word at the right moment.
- **Evolution**: It makes mistakes, but it also reflects. Through the NIT tool protocol and the Reflection self-introspection system, it learns how to understand you better with each interaction.

PeroperoChat is more than a desktop pet app — it's **Pero's "soul container"**; **infOS** is the intelligent runtime kernel that carries it, an AI workstation centered around a "Principal Agent". It has been fully rewritten from Python to a **TypeScript full-stack architecture** (Hono + Vue 3 + Electron), with core high-performance operators implemented in **Rust**: conversations are carried by the Thread model, context is assembled by a read-only compiler, and memories pass through "candidate → gate → canonical memory" — so every bit of warmth rests on clear, auditable engineering.

### 💗 App Experience (PeroperoChat)

> For everyone — no code needed. Install it and start living with your AI companion.

- **🛡️ Cross-platform Unified Memory**: One memory, available everywhere. Whether you chat with Pero on desktop or let it surface in a QQ group or Discord, its memory stays connected — what you talked about this morning, it still remembers tonight. Behind this is the infOS memory engine plus a diary layer that relays memories across scenarios.
- **🎮 Immersive 3D Interaction**: Pero isn't a static image — it's a 3D character with skeletal animation (built on the Bedrock 3D engine). You can drag it, poke it, and it reacts physically; transparent rendering makes it feel like it's floating above your desktop window.
- **🎭 Multi-character Coexistence & Custom Personas**: Want several companions at once? No problem. Each persona file declares a character's personality, which tools it can use, and what it's good at — multiple distinct AI companions can live on your desktop at the same time.
- **🏠 Multi-character Stronghold Rooms**: Put several companions in one "room". Each has its own memory and permissions, yet they can naturally chat with each other — a direct, intuitive expression of "one principal Agent manages the whole, and rooms never overstep each other".
- **🗂️ Saves & Workshop**: Characters, models, and extensions can all be saved, subscribed to, and shared via Steam Cloud and the Workshop, with sources split into **Official / Workshop / Local** tiers. Install and use; switch devices without losing anything.
- **🎨 Pixel + Glass Design Language**: Pixel-art icons + frosted-glass texture, softened with gentle shadows and micro-animations for a light, breathing feel. The whole UI is kept consistent by a custom component library (PButton, PCard, PModal, etc.).

### 🧰 Kernel Capabilities (infOS)

> For developers — this is the "how it works under the hood" part, so there are more technical terms, but each one comes with a plain-language explanation.

- **⚡ Millisecond Associative Memory**: Recalling relevant things from a huge memory store, in milliseconds. It uses a proprietary retrieval algorithm (PEDSA) with the core code written in Rust (the TriviumDB engine), and hits roughly **2.95ms** in a benchmark with 100 million noise entries. During retrieval it also combines semantic decomposition, graph diffusion, and diversity sampling, so results are both accurate and non-redundant.
- **🧠 Principal Agent + Thread Model**: Six things — identity, memory, workspace, context, conversation (Thread), and capabilities — are managed together for each companion. One conversation is one Thread, and the channel (desktop / companion / social / group) decides what context it uses, what it remembers, and what it can do. Whoever is in which window or room stays there; nothing bleeds across.
- **✍️ Read-only Context Compiler**: The prompt fed to the AI isn't assembled ad hoc by the frontend — the backend "compiles" it. History is never duplicated, and every piece of information can answer "why is this in this round's prompt", making it easy to inspect and audit.
- **📜 NIT Tool Protocol**: A small "scripting language" for AI, letting it orchestrate multi-step operations like a mini program (with conditionals, loops, parallelism, and error handling), then execute them through standard tool calls.
- **🔐 CapabilityGate**: A "role × scenario" permission table that declares which tools, skills, and resources each character can use in each scenario. Anything not configured is denied by default — the permission boundary is clear.
- **🏗️ Standalone Backend + Capability Providers**: The backend is a pure Node service that can run independently on desktop, Docker, or servers; the Electron client is just one "capability source" that connects to it. Platform-specific abilities (like screenshots) are delegated on demand, and gracefully degrade offline.
- **🔌 Unified Extension System**: Three extension styles — Skill (teach AI to do something), Tool (give it a new function), and Hook (run code before/after conversations). They can load in-process or communicate across processes (MCP-compatible), so the community can extend them however they like.

### 🧠 Core Idea: An AI Workstation Centered on a Principal Agent

infOS is designed around one central question: what "belongings" should an AI companion own? The answer is six peer **first-class resources**, linked by `agentId`:

| Resource | In plain terms | Authoritative store |
| :--- | :--- | :--- |
| **Identity** | Who it is, how it speaks, its boundaries | Agent definition file |
| **Long-term Memory** | What it remembers | SQLite + TriviumDB |
| **Workspace** | Its personal file space | `@data/principals/{agentId}/workspace/` |
| **Context Runtime** | What the model sees each turn | In-memory (transient) |
| **Thread** | A conversation's boundary and message log | SQLite |
| **Tool Capability** | Which tools it can use, and how much | Agent / extension config |

One key principle: **the backend keeps no "globally active character"**. Which companion lives in which window or room is frontend window-level state; the backend can serve multiple Agents and multiple Threads at once, and switching characters atomically switches or creates the matching Thread.

### ✍️ Context Compilation: Everything the Model Sees Is Explainable

The prompt fed to the LLM is "compiled" by the backend's **Context Compiler**, rather than patched together by the frontend. Each turn, the compiler **read-only** gathers from identity, memory, thread, workspace, and tool capability, producing an LLM message list plus an auditable **Manifest** that answers "why did this information enter this prompt".

Three context layers, each with its own job:
- **Short context**: the raw messages in the recent window, injected as-is and never duplicated;
- **Long memory**: structured facts distilled in the background, retrieved by policy;
- **On-demand retrieval**: memory tools the Agent calls proactively during ReAct decisions.

### 🚀 Main Runtime & Sub-Applications: Context Holding

In AIOS, the principal Agent is the "main runtime". When a task is complex enough to need isolated execution (say, coding or research), it delegates to a **SubAgent** inside an **AgentApplication**.

We use a **"context holding"** model: the SubAgent keeps its own history, compiles its own context, and executes its own tools; the principal Agent only assigns the task, grants resources, and receives results — instead of handing over a fully-compiled context. At the end, the SubAgent returns its output and memory candidates through a **Checkpoint**, and only after the principal Agent's **MemoryGate** approves them do they enter canonical memory.

The payoff is strong isolation: a SubAgent never writes to the main conversation, only uses an authorized tool subset, and only reads a read-only projection of the host persona — so complex tasks don't pollute the principal Agent's conversation or memory.

## 🧠 Memory System Deep Dive

> **"Memory is not keyword matching — it's about association and reasoning."**

> 💡 This section is a **developer-oriented deep dive**; regular users can jump straight to [Quick Start](#-quick-start).

PeroperoChat's companionship is powered by the infOS memory engine — the project's most critical technology. This engine isn't simply "store and retrieve"; it's a full **Perceive → Store → Associate → Retrieve → Reflect** loop: record what happened, recall related memories when needed, and tidy itself up afterward.

All algorithms and performance are carried by the proprietary **TriviumDB** engine (a Rust "vector + graph" database). The rebuilt memory system also adds a "distillation pipeline": **Candidate → Gate → Canonical Memory** — first collect possibly-important information, then filter it, and only then settle it as long-term memory. Every memory also carries **Provenance**, so it can answer: where it came from, why it matters, and whether it has been superseded.

### The Life of a Memory

```
                                        ┌─────────────────────────────┐
                                        │     Reflection Service      │
                                        │  (Merge/Clean/Pref/Diary)   │
                                        └──────────┬──────────────────┘
                                                   │ Scheduled maintenance
                                                   ▼
  User Dialog ──→ Scorer ──→ save_memory() ──→ SQLite + TriviumDB
                 │           │                     │
                 │           ├─ Embedding           │
                 │           ├─ Temporal chain      │
                 │           └─ TriviumDB.link()   │
                 │             (Dual-layer graph)    ▼
                 │                        get_relevant_memories()
                 │                         │
                 │     ┌───────────────────┤
                 │     ▼                   ▼
                 │  Vector search     Graph diffusion (PEDSA)
                 │  (TriviumDB)      (TriviumDB built-in graph)
                 │     │                   │
                 │     └───────┬───────────┘
                 │             ▼
                 │      TriviumDB search_advanced pipeline
                 │      ├─ NMF semantic decomposition (L3~L6)
                 │      ├─ FISTA sparse coding (residual discovery)
                 │      ├─ Co-occurrence boosting
                 │      └─ DPP diversity sampling
                 │             │
                 │             ▼
                 │     RAGPreprocessor injects into Prompt
                 └──────────── ▲
```

### 1. Write Layer: From Dialog to Memory

After each conversation round, the **Scorer ("Secretary")** automatically analyzes the dialog, extracts core events, emotional tendencies, and importance scores, and compresses them into a structured memory:

- **Batch processing**: Multi-round dialogs merged for analysis, avoiding memory fragmentation (batch threshold: 200 messages or 50,000 characters)
- **Auto-splitting**: Oversized contexts are automatically split to avoid exceeding the model's limit (token overflow)
- **Fault-tolerant retry**: Failed tasks are auto-marked and batch-recovered on startup

Three things happen during write:

1. Compute a semantic vector (an "embedding" that turns text into a machine-comparable numeric fingerprint) and write it into TriviumDB's vector + graph storage
2. Maintain a temporal chain (using `prev_id` / `next_id` to record order), stringing memories together by time
3. Use GraphGardener to extract entities and their relationships (causal, associative, containment, etc.), building a "web of concepts" (a cognitive graph)

### 2. Retrieval Layer: PEDSA Pipeline

When the user sends a new message, the retrieval pipeline works in six stages — roughly: coarse recall, then association diffusion, then semantic digging, then gap-filling, then re-weighting, then de-duplication:

| Stage                      | Algorithm               | Purpose (in plain terms)                                                                                      | Implementation                      |
| :------------------------- | :---------------------- | :------------------------------------------------------------------------------------------------------------ | :---------------------------------- |
| ① Vector recall            | Cosine           | Quickly pull out memories with "similar meaning"                                                              | TriviumDB (`search_advanced`)       |
| ② Graph diffusion          | PEDSA + PPR             | Follow relationships between memories to find "seemingly unrelated but actually connected" distant memories | TriviumDB built-in dual-layer graph |
| ③ NMF semantic analysis    | Lee & Seung, 1999       | Break candidates into latent topics to judge the depth and angle of the query                                 | TriviumDB L3~L6 deep manifold       |
| ④ FISTA residual discovery | Beck & Teboulle, 2009   | Find what existing candidates can't explain, triggering a second retrieval for weak signals                   | TriviumDB (`enable_sparse_residual`) |
| ⑤ Co-occurrence boost      | Statistical association | Concepts that frequently appear together get their related memories weighted up                               | GraphGardener                       |
| ⑥ DPP diversity sampling   | Kulesza & Taskar, 2012  | Pick the final results with the "highest quality and least redundancy"                                       | TriviumDB (`enable_dpp`)            |

### PEDSA Three Core Components

Each component handles one thing: **ContextRNN** senses "what we're talking about now", **Leiden clustering** automatically groups memories by topic, and the **feedback loop** corrects itself afterward.

#### A. ContextRNN — Dialog Trajectory Awareness (minGRU)

It's like a continuously-updating "conversation-direction sensor", letting the retrieval system know what direction the conversation is heading. Each round updates a lightweight **minGRU** hidden state in real time (256-dim, ~1.6MB params, <2ms pure-CPU inference):

```
  z_t = σ(W_z @ x_t)                    Gate
  h̃_t = W_h @ x_t                      Candidate state
  h_{t+1} = (1 - z_t) ⊙ h_t + z_t ⊙ h̃_t   State update
```

- **Modulate candidate scoring**: `finalScore = α × vecSim + β × contextAffinity`
- **Modulate graph edge weights**: Guide diffusion along context direction
- **Hidden state persistence**: 256 × f32 = 1KB written to disk, preserved across conversations
- **Implementation**: `@infos/nit-runtime` (Rust N-API) + `ContextRnn` (TypeScript)

#### B. Leiden Clustering — Automatic Community Discovery

Automatically groups memories into topics ("cooking", "work", "emotions", etc.) and retrieves by topic. It's implemented by running the Leiden algorithm on the memory graph, with four benefits:

- **Retrieval diversity**: Select top-3 relevant clusters → take top_k/3 from each cluster
- **ContextRNN synergy**: `cluster_affinities = softmax(h_t @ centroids)` → RNN hidden state selects active communities
- **Diary organization by topic**: Weekly reports organized by cluster
- **Explainability**: Retrieval results carry cluster labels

#### C. Retrieval Feedback Loop — Implicit Signal Collection

After the fact, check whether the AI actually used those memories — reward it if it did, penalize it if not, so the next retrieval is more accurate. After the LLM responds, Jaccard/co-occurrence word matching (no extra token cost) determines whether injected memories were actually used:

- **positive**: Memory key content appears in LLM response → `retrieval_quality += 0.1`
- **negative**: Completely unreferenced → `retrieval_quality -= 0.05`
- **Accumulated triggers minGRU online training**: SGD weight updates, letting the RNN better bias toward useful directions next time

#### Unified Pipeline: PEDSA 7-Step Real-time Flow

```
  User Input ──→  Step 1: ContextRNN updates h_{t+1}
               Step 2: Cluster routing → top-3 active communities
               Step 3: Intra-cluster vector recall (3x over-recall)
               Step 4: Context-aware re-ranking (vecSim + rnnAffinity + centrality + quality)
               Step 5: Graph diffusion (edge weights modulated by h_t)
               Step 6: DPP de-duplication → final top_k
               Step 7: Inject into prompt → LLM → feedback collection
```

### 3. TriviumDB Engine Layer

All vectors, graphs, and retrieval algorithms are unified under **TriviumDB** (the proprietary Rust engine):

- **Vector + graph unified storage**: A `.tdb` file stores both the "similarity index" (HNSW) and the "relationship graph", so a single file can be fully migrated
- **Native dual-layer graph**: One "temporal chain graph" (ordered by time) + one "entity concept graph" (ordered by concept relations), both written through the same interface
- **Three-layer memory isolation**: Each companion has its own independent memory store; social and desktop indirectly connect through a shared diary layer

### 4. Four-Layer Memory Storage

Memory is stored in four layers by "freshness" — the higher the layer, the more "in the moment"; the lower, the more "long-lasting":

| Layer                 | Carrier            | Content                          | Retrieval Method        | Lifecycle |
| :-------------------- | :----------------- | :------------------------------- | :---------------------- | :-------- |
| **Layer 0 (Working)** | JSON / LLM Context | Current session context          | Sequential read         | Short     |
| **Layer 1 (Vector)**  | TriviumDB          | Raw segment vectors + text index | Semantic similarity + keyword | Long |
| **Layer 2 (Graph)**   | TriviumDB          | Entity/event graph + edges       | Association diffusion + graph query | Long |
| **Layer 3 (Diary)**   | SQLite / TDB       | Daily/weekly summaries           | Keyword + timeline      | Permanent |

### 5. Reflection Layer: Autonomous Memory Maintenance

Besides responding, memory also "organizes itself". **ReflectionService** runs periodically, executing 7 maintenance tasks:

1. **Importance annotation + thought cluster classification** (single LLM call, merged)
2. **Memory consolidation**: Compress low-importance stale events into declarative summaries
3. **Erroneous memory audit**: LLM identifies and cleans contradictory, duplicate, and hallucinated memories
4. **Social diary deduplication**
5. **Preference extraction**: Distill long-term user preferences from event memories
6. **Boundary maintenance**: Handle zombie/over-age memories
7. **Dynamic line updates**: Generate personalized greetings and small talk based on recent memories

All maintenance operations are recorded and support one-click rollback.

## 🔌 Extension System

> **"From loading a Skill to running an independent microservice — you decide how deep to go."**

Want Pero to learn new abilities? The extension system is built for exactly that. infOS provides three extension types, freely combinable within a single extension package:

```
     Skill              Tool               Hook
  ┌───────────┐   ┌───────────────┐   ┌──────────────┐
  │ Task      │   │  Atomic       │   │ Lifecycle    │
  │ Knowledge │   │  Tool (func)  │   │ Event Hooks  │
  ├───────────┤   ├───────────────┤   ├──────────────┤
  │ SKILL.md  │   │ handler()     │   │ pre_chat     │
  │ Progressive│  │ JSON Schema   │   │ post_chat    │
  │ Loading   │   │ params        │   │ on_event     │
  └───────────┘   └───────────────┘   └──────────────┘
   AI on-demand     Standard tool call   Message pipeline
```

- **Skill**: Written in YAML + Markdown, like an instruction manual for "how to do something". The AI loads the steps on demand, so the context is never flooded all at once.
- **Tool**: Gives the AI a new function it can call, with parameters declared via JSON Schema.
- **Hook**: Event listeners/interceptors that can run before a chat, after a chat, or on specific events.

Two communication modes: **in-process** (loaded directly as TypeScript/JavaScript) or **cross-process** (over standard input/output, MCP-compatible).

## 💬 Social Mode

**Let Pero step out of the desktop and into your group chats~**

infOS lets AI interact like a real user in QQ groups and private chats. The "four-layer decoupled" architecture below is what keeps multiple platforms (QQ, Discord, Telegram, etc.) cleanly pluggable.

### Four-Layer Decoupled Architecture

```
Layer 0: Bridge (SocialBridge — lands messages and notifies the frontend)
  └── Message persistence + Frontend state notification

Layer 1: Scheduling (SessionManager + Scheduler, platform-agnostic)
  └── Four-state machine: observe → summoned → active → dive
  └── Batching logic (private 7s / group 15s) + Secretary layer decisions

Layer 2: Abstract interface (AbstractSocialAdapter)
  └── Unified connect / disconnect / sendMessage

Layer 3: Platform adapters (NapcatAdapter / DiscordAdapter / TelegramAdapter)
  └── Each handles its platform's protocol (e.g. QQ's OneBot v11 / CQ code)
```

- **Cross-scenario memory**: Social chats are also distilled into graph memories by the "Secretary"; desktop and social share a diary layer, so memories stay connected.
- **Smart batching**: In a lively group chat, the AI observes for a while, understands the flow, then gracefully "surfaces" — instead of replying to every single message.
- **Social daily reports**: Automatically reviews the day's social records, turning them into diary entries that settle into long-term memory.

```bash
# Clone the repository
git clone https://github.com/YoKONCy/infOS.git
```

| :------------------ | :----------------- | :------ |
